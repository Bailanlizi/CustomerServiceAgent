## 痛点三（流程反复 / 话术循环）现状诊断与改进行动分析

- 诊断：CustomerServiceAgent（LangGraph）在"记忆 / 状态 / 转人工"三处有结构性缺口：
  1. state.history 为死字段，app/api/v1/chat.py 恒传 []；
  2. generate() 对 ORDER/POLICY 路径完全不喂 state["messages"] 历史 -> 字面"单轮无状态记忆"；
  3. 会话历史仅存 Redis checkpoint，聊天热路径不写 message_cards（仅 admin/退款写），Redis 超时即丢；
  4. 前端 customer_ui.py 用 int(time.time()) 生成 thread_id，每次刷新重建 -> 重连/转人工即重说；

- 下一步方向（待用户确认）：先止血（稳定 thread_id + 聊天历史落库 + generate 喂历史）-> 分层记忆+对话状态机 -> Supervisor 重构 + handoff 闭环。先不动代码。

## 7 维度架构梳理（Goal/State/Model/Tools/Memory/Planner/Evaluator）

- Goal：电商客服 v4.0 = 政策咨询 / 订单查询 / 退款办理 + 人机协作（FA + RAG + 硬规则 + 风控 + 审计）。

- Model：业务 LLM = ChatOpenAI(qwen-plus, t=0)；Embedding = text-embedding-v3, dim=1024, HNSW(m=16, ef=64)；结构化输出 PolicyAnswer / IntentDecision；Judge LLM 强制与业务模型解耦。
- Tools：仅 refund_tools（3 个），其他意图无工具。check_/submit_/query_refund_status + InjectedState(user_id, thread_id) + AuditLog 自动落库。

- Planner/Policy：单层路由（intent_router + route_intent），无 Supervisor、无对话状态机、无 slot-filling。检索规则：pgvector cosine + SIMILARITY_THRESHOLD=0.5 + FAQ 重排。
- Evaluator/Guardrails：(1) PolicyAnswer 引用校验 (2) 检索阈值 (3) 双兜底答语 (4) InternalLLM tag 屏蔽流式泄露 (5) RefundEligibilityChecker 硬规则 (6) AdminDecisionRequest REJECT 强制备注 (7) eval/*.jsonl + chinese_ragas_prompts + metrics.py（primary_hit@k / clause_recall@k / MRR / nDCG / 引用精度）。
- 已识别设计漏洞：history 死字段、ORDER/POLICY 路径零历史、转人工无 handoff 上下文包、聊天历史不落库、thread_id 不稳定、无 Supervisor / 槽位 / 计划-执行。

## codex 观点对齐（Case 驱动 vs Supervisor）

- 整体方向认同：下一阶段最优先的不是 Supervisor，而是 Case/Ticket 作为跨轮 / 跨渠道 / 跨人工的事实载体。
- 三类状态必须分开：①短期会话（LangGraph checkpoint，已就绪）②案件工作记忆（Case，需新建）③长期记忆与知识（RAG + 实体偏好，partial）。
- Handoff 必须是结构化 package（client goal / confirmed facts / done actions / pending slots / risk / next step / 系统 ID），不是原始 transcript。
- 同意"不要立刻上多 Agent 自由转交"，保留 Router + Case Manager + Specialist + Handoff，Supervisor 后置。
- 同意"通用 Plan-and-Execute 不适合客服"，用显式 FSM（INTAKE → IDENTIFY → COLLECT → CHECKED → CONFIRM → HUMAN → RESOLVED）。
- 我的差异点 1：P0 必须"止血 + 立 Case"并行。只立 Case 表但聊天不落库 / thread_id 不稳，Case 表就是空的。两者要在同一 PR 内完成。
- 我的差异点 2：Specialist 先用 node 共享 state，等真出现"上下文隔离"压力（POLICY 检索证据回流污染 ORDER 状态）再切 subgraph。subgraph 切换成本高，过早切是过度工程。
- 验收指标转换：从"回答流畅度" → "Case 续接成功率 / handoff 包字段完整率 / 重复澄清次数 / FSM 状态转移耗时 / 话术相似度"。
- 技术选型无需更换：LangGraph checkpoint + Postgres + Redis + pgvector 原班人马，Case 直接落 Postgres，AuditLog 吸收为 case_events 子集而非新做一套审计。

### 核心结论：P0 整体质量较高，但有 4 处高严重度问题必须 P1 修复前先处理

**高严重度（必修）**
1. submit_refund_application 未自动注入 working memory（order_sn/reason_detail 仍由 LLM 自由声明）— 工作记忆字段只用作 prompt 提示，工具调用参数仍由 LLM 编造，违反 codex "能力注册表 + 前置校验" 的原意。
2. active_order_id 在 REFUND 路径下不会进 memory（REFUND 走 refund_agent→ToolNode，不再经过 query_order 节点，order_data 字段为 None）— persist_turn 的 order_data 分支是死代码。
3. refund_reason 是 free-text，但 submit 工具需要 reason_category enum，两者语义未对齐 — refund_agent 不知道要把 free-text 映射成 enum。
4. intent_router 在 active_domain 已有时无脑复用，不识别 explicit_new_goal=True 的目标切换意图 — 当用户从 POLICY 切到 REFUND 且 LLM 返回 domain=OTHER 时会被截胡。

**中严重度（建议修）**
- history 字段仍是死字段（chat.py:79 硬传 []）— 与 messages 双重历史造成认知负担，建议删除。
- 摘要阈值 12 轮偏长（客服平均 4-8 轮）；保留 3 轮可能裁掉关键中间事实（建议 6 触发 / 5 保留）。
- RemoveMessage + REMOVE_ALL_MESSAGES 在 aupdate_state 路径的行为可能不一致，需补一条端到端测试验证压缩后 checkpoint。
- LLM 异常兜底未携带 explicit_new_goal 语义 — 用户从 ORDER 切 REFUND 且 LLM 故障时兜底分类失效。
- 测试覆盖：4 个测试覆盖合并槽位 / 换单清空 / 摘要校验 / 保留 3 轮；缺并发合并（version mismatch）、LLM 兜底、阈值触发、压缩端到端 4 个用例。

**低严重度（按需修）**
- default_working_memory() 与 AgentState 字段两份 schema，未来加字段需同步两处。
- _extract 兜底词表只覆盖中文，英文会路由到 OTHER。
- prompt 序列化整个 memory → LLM 看到所有内部状态（订单 ID / 用户约束）— token 成本与隐私风险小，但建议收紧到必要字段。
- audit_logs 没有 conversation_id 字段，P1 阶段改造按 case 维度 admin 工作台时需要补。
