## 评估模块二次分析：延迟 / token / 模块优化（不动代码）

应"分析延迟、token 能否取真实总值、模块如何优化"请求，仅静态分析 `eval/runs/` 与 `scripts/eval_agent_e2e.py`、`run_rag_baseline.py`。

### 1) 延迟：高度分化，根因是 LLM endpoint，非应用逻辑
- 逐场景节点耗时（041503, N=5）：S01 37 / S02 25 / S03 353 / **S04 11614** / **S05 25489** / S06 21 / S07 133 / S08 37 ms。单 run 合计≈37.7s，其中 S04+S05 = 37.1s（占 98.4%）。
- 6/8 场景 <400ms（优秀）；S04(~11.6s)、S05(~25.5s) 灾难级。
- 时间出在哪：LLM 生成调用单 call 5.8–12.3s（S05 generate 12.3s、S04 identify_order+refund_agent 各 5.8s）是绝对主导；应用编排节点（entry/dispatch_router/route_from_entry/check_eligibility/submit/compose_answer/query_order）全部 <200ms；检索 retrieve 864ms 是确定性第二大头。
- 优化抓手（仅 LLM 侧可控）：① S04 无单号退款却跑 2 个 LLM call(identify+refund_agent) 共 11.6s 才反问单号 → 可在"无订单标识且非确认"时短路直接反问，省 11s；② S05 generate 12.3s 单 call → 换更快/更小生成模型、压 prompt、开 prompt caching（system+policy_rules 静态）；③ retrieve 864ms 可优化向量索引/embedding 维度或缓存高频问；④ 流式输出降低感知延迟。

### 2) token：今天取不到真实总值（系统性低估）
- `install_token_callback` 对 `ChatOpenAI.astream` 只记 `{"kind":"astream","prompt_tokens":None,"completion_tokens":None}`（eval_agent_e2e.py:110），**流式调用 token 被丢弃**。
- 全量 11 次 run：ainvoke=145 / astream=13（8.2%）；干净 run 041503：60 次调用中 5 次 astream 丢 token（8.3%）。且丢弃的正是最贵的大生成 call（S04 的 identify_order 等），低估幅度不成比例。
- 报告值 prompt 23,787 / completion 27,368 是**下界**，真实总值更高。
- 修法（描述，未改代码）：OpenAI 流式末 chunk 带 usage（或 `stream_options={"include_usage":true}`），在 `_astream` 中累加 `chunk.usage_metadata` 后即可补全；ainvoke 已正确读 usage_metadata。

- P0 可靠性：温度已固定 0（nodes.py:36 / state_manager.py:111），故此前 S03/S06/S07/S08 偶发失败**非采样随机，是 harness 耦合/状态问题**（如 S08 依赖同进程 S03 先建单、跨 run 隔离不足）→ 应让场景自包含、清除调试/退化 run 后再报"重复测量"，并给置信区间。
- P1 指标覆盖：补 answer_correctness / context_recall / answer_relevancy（或事实点对齐）替代"仅靠 faithfulness+条款召回"；给最终 baseline_p1 管线补一份 faithfulness。
- P1 RAG 评估缺分阶段延迟/token：`run_rag_baseline.py` 仅记整体 `duration_seconds`（line 123/137），无 retrieve-vs-generate 拆分、无 token；应补。
