## RAG 模块专项梳理（只读分析）
- 架构：离线 ETL 入库 + 在线余弦检索，向量存 PostgreSQL pgvector。
- 数据三层：原始文档 `data/*.md`（return_refund_policy.md / shipping_policy.md）→ `knowledge_chunks` 表（pgvector）→ HNSW 余弦索引。
- 表结构（app/models/knowledge.py）：content(text) + embedding(Vector(1024)) + source + meta_data(JSON:{page,chunk_index}) + is_active + 时间戳；维度读 config.EMBEDDING_DIM=1024，init_db() 建 vector 扩展。
- 入库（scripts/etl_policy.py，离线手动）：glob 扫 data → 按扩展名选 loader → RecursiveCharacterTextSplitter(500/50, 中文分隔符) → 幂等清理(delete by source) → 分批 embed(BATCH 50, tenacity 重试3次) → 分批入库(100/批)。
- 检索（nodes.py retrieve）：POLICY 意图 → aembed_query → cosine_distance order by limit 5 → 硬阈值 distance<0.5(SIMILARITY_THRESHOLD) → context 交 generate。
- 关键问题：
  1. **两套 embedding 客户端真源不唯一**：ETL 用 langchain_openai.OpenAIEmbeddings（未传 dimensions），检索用自研 QwenEmbeddings（显式 dimensions=1024）——维度靠模型默认值对齐，改 EMBEDDING_DIM 即错位。
  2. 单向量 + 硬阈值，无 rerank/多路召回/query 改写（RAG P1 增强点）。
  3. 知识库静态：改数据要手动重跑 ETL，无增量/版本管理。
  4. meta_data 利用率低（只存 page/chunk_index，无章节/类型等结构化元数据）。

## RAG 评估测试集构建（eval/testset.json）
- 用户评估思路（五步：准备问答→检索器→生成器→组装四组数据→RAGAS 评估）方向正确，即 RAGAS 标准管线。已校正 3 点：
  1. 四组数据对齐 RAGAS 字段：question / answer(LLM生成) / contexts(检索chunk) / ground_truth(手写标准答案)。
  2. 检索器+生成器必须复用项目现有逻辑（QwenEmbeddings+pgvector余弦top5+0.5阈值；GENERATE_SYSTEM_PROMPT），不能另写理想版，否则评估失真。
  3. ground_truth 与「应命中条款编号」分离：ground_truth 只写纯语义（供 answer_correctness），expected_sources 单独存条款编号（供检索命中精确校验，RAGAS 不自动判编号）。
- 产出：eval/testset.json，45 题，字段 id/question/ground_truth/expected_sources/category/difficulty。
- 六维度分布：层级冲突6(VIP>品类>通用)、量化细节10、品类边界9、抗幻觉8、基础事实6、多跳综合6（合计45）。
- 关键设计：expected_sources 第 1 个为主权威条款，FAQ_xxx 为次优命中（FAQ 是引用式转述）；difficulty 分 easy(单条款)/medium(边界量化)/hard(多条款冲突或多跳)。
- 下一步（未做）：写检索器脚本（复用现有 retrieve 逻辑）、写生成器脚本（复用 GENERATE_SYSTEM_PROMPT）、组装 EvaluationDataset、跑 RAGAS。指标建议：检索侧 context_precision/recall/relevancy，生成侧 faithfulness/answer_relevancy/answer_correctness。
