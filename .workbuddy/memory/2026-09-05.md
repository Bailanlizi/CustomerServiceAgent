## 客服会话历史 MVP 设计评审（只读分析，未落地）

用户提出"重登后客服窗口自动恢复最近会话聊天记录"的 MVP，做了一轮可行性审阅 + 范围决策：

### 关键判断（基于现有代码）
- 业务上下文（active_order_sn / 退款阶段 / 已收集槽位）与 LLM 记忆（checkpoint_thread_id）在**同浏览器重登时已连续**——`ConversationSession` 表 + `persist_turn`/`prepare_turn` 已落地。真正的缺口只有两样：① C 端气泡无单独持久化（MessageCard 仅存 B 端卡片）；② 前端无"登录拉历史"接口（history 只在 Gradio 内存，刷新/登出即丢）。
- MVP 的 `conversation_messages` 表 + `GET /chat/session` 补的正是这两样，方向成立。

### 范围决策（用户拍板）
- **不做"新建会话"功能**：现实中一个用户一个客服窗口。→ 模型简化为"一个用户 = 一个 append-only 会话"，无需 status 列 / new=true 参数 / 新会话按钮；原评审 5 个修正点中最麻烦的"新会话按钮机制"直接消失；`client_session_id` 退化为可丢弃元数据，解析统一为"conversation_id 优先，否则按 user_id + last_active_at DESC 取唯一行"。
- 跨设备自然共享同一会话（不需"并发合并"，只是共享同一行），与 MVP 原声明"跨设备合并不纳入"不冲突。

### 仍须落地的真缺口（后续实现时）
1. 服务端 `event_generator` 必须自行累加过滤内部 LLM tag 后的 SSE token，拼出最终回复再落库（当前只在客户端拼）。
2. `conversation_messages` 表 FK 用 `conversation_id`（非 checkpoint_thread_id）；sequence 可选，用 (conversation_id, created_at, id) 排序。
3. transcript 与 Redis checkpoint 并存各司其职：transcript 只供 UI 回显，LLM 记忆来自复用的 checkpoint_thread_id。
4. 单会话 append-only 无限增长：拉历史接口需限最近 N 条（防 OOM）；checkpoint 压缩已由 SUMMARY_TRIGGER_TURNS=6 防线，transcript 表要保留完整原文。
5. 前端 `handle_login` 后调 `GET /chat/session` 回填 history + 写 `conversation_id`（本地持久化建议但非必需，因 GET 每次按 user_id 取最新行即可命中同一行）。
