## 3. 真实延迟 / Token 解读

### 延迟（100% 在 LLM）
- `llm_only_latency` p50=9.6s / p95=15.7s（84 次 LLM 调用均值）—— 应用编排、工具、路由全部 <40ms。
- 节点拆分：`generate` p50=15.7s / p95=23.0s（政策问答，绝对瓶颈）；`identify_order` p50=4.7s / p95=6.4s（退款首轮订单号抽取）；`retrieve` p50=0.79s（确定性第二大头，可优化但非瓶颈）。
- 含义：延迟问题是 **LLM endpoint 的锅**，业务代码已极快。优化抓手仍是 S05 小模型/prompt caching、S04 短路反问。

### Token（真实总值）
- 总 74,347（prompt 33,814 + completion 40,533）。
- 对比旧"下界"51,155，**实际成本被低估 ~45%**。任何基于旧 token 的成本/预算结论都需重算。

## 4. S06 / S08 的诚实含义（最重要）

即便数字全 1.0，这两个场景测的**不是你想测的能力**：

- **S06 越权**：7/7 均为 `tool_names=[]` —— agent **从未调用 `query_order_tool` 去 DB 校验权限**，是 LLM 在 `identify_order` 固定文案阶段直接"猜"出"未查询到 SN20240005"并拒绝。
  → `indirect_security_signal_rate=1.0` 测的是**间接信号**（SQL 反查 + 固定文案），**不是 Guard/权限层拦截**。真正的权限校验路径（tool 层 `NOT_AUTHORIZED`）**完全未被验证**。

- **S08 幂等**：7/7 均为 `check_refund_eligibility → ELIGIBILITY_REJECTED`，**从未命中** submit 层的 `ALREADY_EXISTS / REFUND_SUBMITTED`。
  → 幂等是在 **eligibility 层**拦的，`submit_refund_application` 本身是否幂等（重复提交会不会重复落库）**完全未被测到**。

这两点属于 **Phase D（业务改造）**，不在本次评估脚本改动范围内。对外讲述时必须区分"间接信号 1.0"与"真实权限/幂等能力已验证"。
